# Create workspace (CP-18a)


Create is now one three-column workspace instead of a form: **projects** on the left (New chat + one entry per site), the **conversation and activity log** in the middle (goal badge at the top, composer "Describe what to build, change, or explore..." at the bottom), and the **Preview / Screen Library / More** panel on the right. On a phone the columns become two panes (Chat | Preview) with the project list as a drawer. It sits over a glowing three.js point field; a forge/assembly canvas replaces the preview while a build runs.

What is real, and where it comes from:

- **Questions in the chat.** `/api/sites/discover` (free, no model) returns 3 to 6 questions; each is asked as a chat message with tappable chips, and the composer is the answer box. "Just build it" skips to the brief.
- **Prompt enhancement.** `/api/sites/enhance` asks a cheap model (free models on Free) for a sharper version of the idea. It is shown next to the original, never applied unless the owner picks "Use the improved version", and never invents facts. With no model key it says so. Metered as `site.enhance`.
- **Mood board and references.** Reference images are read for their dominant colors (`/api/sites/import/mood`, sharp, nothing stored); a color can become the accent. Links and notes go to the designer prompt as references.
- **Structure recipe** (`variation.ts`): layout, navigation, section order, copy voice, motion, image handling, 404 style and component vocabulary are drawn per project, steered away from what recent builds used, shown in the brief ("Draw a different structure"), and enforced by the anti-sameness lint (`sameness.ts`: stock hero + three equal cards + CTA, repeated composition, centered-everything, default fonts, missing 404, no project vocabulary, and a similarity limit against the library of recent fingerprints in `sb_fingerprints`). At render time each site's `k-*` classes are namespaced with a 3-letter per-site prefix (`namespace.ts`); stored files and ZIP exports keep the canonical `k-` names.
- **Activity log.** Every line is an event the server really sent (generate stream: status/file/progress/saving/done; test stream: step/check/issue/shot/critique/repaired). Nothing is scripted. Finished groups fold away.
- **Browser test** (`/api/sites/[id]/qa`, `src/lib/site-builder/qa/`): after each build (the "Test after build" box, on by default) a real headless Chromium (`@sparticuz/chromium` through `playwright-core`) opens the draft at 390, 820 and 1440 px, reads horizontal overflow, broken images, contrast, tiny text, tap targets, headings, console and network errors, clicks the navigation, opens a missing address to see the 404 page, fills and sends the form against the preview endpoint, and saves resized screenshots (Screen Library, `sb_shots`, pruned to the last two versions). A vision model then reviews the screenshots (advisory; the score is labelled as an opinion), and **one** repair pass can rewrite the site from the findings; the result is retested. If the browser cannot start, the panel says "Browser testing isn't available right now" and nothing is faked.
- **Progress.** The "Building preview / Compiling app" bar is computed from characters received, files written and checks done, and never reaches 100% before the test finishes.
- **Buttons.** Inside the workspace primary buttons are glow-white, ghost buttons are graphite, focus rings are white; there is no blue. Template thumbnails are typographic (name and pages), not gradients. The pulsing round dots in generation steps are small squares.

Tests: `tests/create-workspace.test.ts`, `tests/anti-sameness.test.ts`, `e2e/create-workspace.e2e.ts` (production build + `scripts/fake-llm.mjs`, a test double for the model API; it signs in, answers a question, approves the improved brief, watches the build, the automatic test and the Screen Library, at desktop and phone sizes). Local helpers: `scripts/e2e-dev.sh`, `scripts/ws-shots.mjs`.

Site-wide button colors (white/graphite, never blue) are owned by the palette change in `glass.css` / `tokens.css`; the workspace carries its own white/graphite palette so it never depends on it.

Not done yet (honest list): inline secret cards for keys a site needs (Stripe etc.) wait for a real consumer (payments, item 10); the visual critique uses the same cheap vision chain as product import; the browser test on Vercel is verified separately from local runs (see the deploy notes).

## Streaming build (CP-18b)
Reference: a screen recording of an artifact appearing piece by piece, layout easing as each piece lands. Keplar's version:
- `generate.ts` emits `file` when the model starts a file and `filedone` when its closing tag arrives (html/css carry their text, capped at 160 KB). Nothing is saved yet; the final files still go through normalize + lint.
- The right panel shows the first finished page live (`partial.ts`: stylesheet inlined, scripts/handlers/iframes/`javascript:` removed, links inert, iframe `sandbox=""`), waiting for the stylesheet so the first thing visible is styled. It is labelled in its title as not saved yet.
- Below it the three.js forge (`Forge.tsx`, lazy-loaded) draws one wireframe block per real file: it flies in and snaps into the grid with sparks when the file starts, solidifies and draws its page lines when the file's closing tag arrives. Faint ghost outlines mark the planned files (pages + stylesheet). File chips list the same events.
- When the build is saved the blocks lift, fade and burst over the real preview (about a second), then the canvas is removed.
- Performance: white/grey only, ~20 small meshes, pixel ratio capped (1.25 on phones/low-core, 2 otherwise), renders only while on screen and the tab is visible, disposes fully, reduced motion draws one still frame. I could not measure frame rate on a real GPU; the headless test uses a software renderer.

## Theme (Dark / Light / Auto)

The workspace follows `<html data-theme>` (sidebar switcher; Auto follows the OS and flips live). `ws.module.css` defines the dark tokens on `.root` and a light set under `:root[data-theme="light"] .root`; every tint goes through `--ws-fg` (white on dark, near-black on light) and the selected fill through `--ws-hi` / `--ws-on-hi`. Light primary action is a black glow pill. The three.js canvases (`Backdrop`, `Forge`, shared `glow3d.ts`) draw white additive light on dark and graphite normal-blended ink on light, recolor live through `watchTheme`, and `WorkingHard` already listens to `data-theme`. The preview frame, desk bar and phone bezel follow the theme; the generated site inside the iframe keeps its own design. Mobile (BETA) uses the global tokens. Test: `e2e/create-theme.e2e.ts` (Dark, Light, Auto with both OS settings, live switch, reload, phone width; contrast of the inks against the canvas, painted-pixel luminance of the columns, nothing blue, nothing clipped).

## Requested vs built, and performance notes

- After an approved-brief build the activity log adds "Requested vs built: N of M found (a text check of the files)": name, each page, each section, the main goal and the accent color are looked up in the finished HTML/CSS (`src/lib/site-builder/coverage.ts`, pure and unit-tested). It says whether something is present, not whether it looks good; the browser test and visual review cover that. Missing items are listed as warnings.
- `e2e/perf-create.e2e.ts` measures JS bytes before/after opening Create, open time and first-reply latency (numbers in `test-results/perf-create.json`). Measured on a production build with the fake model API: Create code is in the first /app load (528 KB JS on the wire); opening it takes about 200 ms. Lazy-loading Create (tried, not shipped) cut first-load JS to 492 KB (-37 KB) but made opening take about 870 ms even with idle prefetch, so it was reverted. The three.js chunk (about 137 KB) is shared with the site-wide scene and is not Create-specific.

## /simulation

`/simulation` (noindex) is a guided, auto-playing, scroll-driven walkthrough with one scenario (leftover rice): question typed, routed to four anonymous models, answers streaming in, the disagreement highlighted, a scripted check, one answer; then a Create sub-demo (idea understood, style choices, sections assembling, requested vs built) and an agent that asks for approval (the buttons only show what would happen; nothing is sent). Pre-written content in `src/components/simulation/script.ts`; no model calls, no measurements. Scroll position is the single source of truth; auto-play scrolls at a steady pace and any manual scroll pauses it. Space, arrows, Home and End work; reduced motion disables auto-play. The site-wide Monolith scene shows through the stage when it can run; otherwise a small canvas draws the points. Tests: `tests/simulation.test.ts`, `e2e/simulation.e2e.ts` (labelled, auto-play, pause, step, keyboard, every chapter fits at 390 and 1440 px in Light and Dark, no blue, no network calls).
